Problema

Definição. Um problema é definido por uma entrada, que descreve os recursos e informações que podem ser usados na solução do problema, uma saída, que descreve a solução esperada do problema, e uma descrição precisa e objetiva do problema em si, que usualmente é formulada em forma interrogativa (pergunta).


Nome do Problema

Enunciado/pergunta do problema, evidenciando a relação entre a saída e a entrada.

Entrada: Recursos/informações para solucionar o problema.

Saída: Descrição da solução esperada.

Provando que um problema não tem solução computacional

Tipicamente, para provar que um problema P não tem solução computacional se usa 2 estratégias:


  • Contradição: mostrar que se a solução do problema P fosse computável, um paradoxo seria gerado, ou;


  • Redução: mostrar que um problema que não tem solução computável é um caso especial do problema P.

Meta-Programação

  • É uma ótima forma de generalizar diversos procedimentos


  • Permitiu a construção de computadores de propósito geral


  • Porém, também pode gerar paradoxos: o que acontece se um programa analisa ele próprio?

Testando Terminação

pára?

Obj: Dado um programa P e uma entrada E para P dizer se P pára (termina) ou não quando executado sobre a entrada E.

Entrada: Programa e entrada.

Saída: Pára ou não pára.

Vamos assumir que existe um programa chamado pára? que resolve este problema, ou seja, assumimos que o problema tem solução computacional.

Lembre que podemos codificar todos os programas como números (bem como todas as entradas), então este programa poderia receber apenas números como argumentos …

Programa H

Vamos analisar o comportamento de H:

  • Se H pára para entrada H, então H entra em loop (não pára); Portanto, H sobre entrada H não pára: CONTRADIÇÃO.

  • Se H não pára, H devolve 1 (pára). Logo, H sobre entrada H pára: CONTRADIÇÃO.

Portanto, se o programa pára? existir, chegamos a um paradoxo!
Logo, concluímos que
pára? é não-solucionável!

Prova por Redução

  • A prova de que Passa nos testes? não tem solução computacional foi feita por redução.


  • Redução é a técnica mais usada, pois normalmente é mais fácil comparar problemas do que encontrar um paradoxo.

Questões

  • Qual a relação entre a ideia da redução de problemas e reúso?
    • Para poder reusar, precisamos transformar o problema (ou parte do problema) que queremos resolver em um problema que já está resolvido.


  • Além da transformação sintática (das entradas/saídas), o que é fundamental para transformar um problema em outro (ou seja, fazer a redução)?
    • É fundamental que haja compatibilidade semântica entre os problemas para que o problema que será usado de fato resolva o problema que queremos.


  • Por que o conceito de transformação é fundamental para resolver problemas?
    • Porque quase nunca resolvemos um problema do zero, sempre usamos algum módulo que foi construído por outra pessoa, e para fazer esse uso garantindo a correção de nossa solução, é necessário verificar a compatibilidade sintática e semântica, ou seja, que esse uso realmente configura uma redução.

O que é um algoritmo eficiente?

Podemos analisar eficiência sob diferentes aspectos:

  • Tempo
  • Espaço
  • Energia
  • Mensagens trocadas
  • …


Normalmente, se avalia eficiência de forma abstrata para a análise ser independente de uma máquina concreta.

Ordens de Grandeza

  • Definimos ordens de grandeza para avaliar a eficiência de soluções computacionais
  • Essas ordens de grandeza descrevem limites para as funções que representam a eficiência de um algoritmo:


Dado um tamanho de entrada, quanto tempo (espaço, energia, etc) é necessário para o algoritmo gerar a solução?

Ordens de Grandeza

  • O(1) – constante
  • O(n) – linear
  • O(\log n) – logarítmica
  • O(n^2) – polinomial
  • O(2^n) – exponencial
  • O(n!) – fatorial

Exemplo 1

fun tamanho(l :: List<String>) -> Number:
  cases (List<String>) l:
    | empty => 0
    | link(f, r) => 1 + tamanho(r)
  end
end
tamanho([list: "a", "b", "c"])
1 + tamanho([list: "b", "c"])
1 + 1 + tamanho([list: "c"])
1 + 1 + 1 + tamanho([list: ])
1 + 1 + 1 + 0 = 3
  • Qual é a relação entre o comprimento da entrada e o número de recursões?
  • O número de recursões para uma lista de tamanho N é na ordem de O(N).

Exemplo 1

fun tamanho(l :: List<String>) -> Number:
  cases (List<String>) l:
    | empty => 0
    | link(f, r) => 1 + tamanho(r)
  end
end
tamanho([list: "a", "b", "c"])
1 + tamanho([list: "b", "c"])
1 + 1 + tamanho([list: "c"])
1 + 1 + 1 + tamanho([list: ])
1 + 1 + 1 + 0 = 3
  • Quanto maior a entrada, mais passos de recursão são necessários.
  • O número de passos entre as chamadas recursivas é sempre o mesmo.

Exemplo 2

fun contem-b(l :: List<String>) -> Boolean:
  cases (List<String>) l:
    | empty => false
    | link(f, r) => if f == "b":
        true
      else:
        contem-b(r)
      end
  end
end
  • O número de passos varia conforme a entrada. Consideramos melhor caso, pior caso ou caso médio?
  • O número de passos (chamadas recursivas) para esta função chegar ao resultado é, em média, N/2, sendo N o tamanho da entrada.
  • Portanto, este algoritmo tem complexidade de tempo na ordem de O(N).

Exemplo 3

fun maior(l :: List<Number>) -> Number:
  ask:
    | is-empty(l.rest) then: l.first
    | maior(l.rest) > l.first then: maior(l.rest)
    | otherwise: l.first
  end
end
Expressão Requer 2 avaliações de
maior([list: 0, 1, 2, 3]) maior([list: 1, 2, 3])
maior([list: 1, 2, 3]) maior([list: 2, 3])
maior([list: 2, 3]) maior([list: 3])
  • No pior caso (lista crescente), cada chamada faz 2 chamadas recursivas: T(n) = 2\,T(n-1) + c.
  • Esta função tem complexidade de tempo de O(2^n) — exponencial!

Exemplo 3

fun maior2(l :: List<Number>) -> Number:
  ask:
    | is-empty(l.rest) then: l.first
    | otherwise:
      maior-do-resto = maior2(l.rest)
      ask:
        | maior-do-resto > l.first then: maior-do-resto
        | otherwise: l.first
      end
  end
end


Complexidade:

  • Esta função tem complexidade de tempo de O(n).

Exemplo 4

fun ordena(l :: List<Number>) -> List<Number>:
  doc: "Dada uma lista de números, retorna a lista ordenada em ordem crescente."
  cases (List<Number>) l:
    | empty => empty
    | link(f, r) => insere(f, ordena(r))
  end
end

fun insere(n :: Number, l :: List<Number>) -> List<Number>:
  doc: "Dado um número e uma lista ordenada em ordem crescente, insere o número na lista mantendo-a ordenada."
  cases (List<Number>) l:
    | empty => link(n, empty)
    | link(f, r) => ask:
        | n < f then:
          link(n, l)
        | otherwise:
          link(f, insere(n, r))
      end
  end
end
  • Quantas chamadas recursivas esta função executa em média para chegar ao resultado?

Classes de Complexidade

  • Pode-se definir o custo de resolver problemas e usar esses custos para classificar os problemas em classes de complexidade.

  • Existem muitas classes de complexidade, mas as mais importantes são as classes de problemas tratáveis (que podem ter solução computacional eficiente).

Limites do Tratável: Classes P e NP

  • P: Problemas que podemos resolver em tempo polinomial.
    • Ex: Maioria dos problemas que vimos nesta disciplina, ordenação, …


  • NP: Problemas para os quais podemos verificar uma solução em tempo polinomial.
    • Ex: Não conseguimos encontrar um ciclo em um grafo que passe por todos os vértices em tempo polinomial. Mas dado um ciclo, podemos verificar que ele passa por todos os vértices em tempo polinomial.


  • Não foi provado se estes conjuntos são iguais ou não!
    • Consenso: não são.

P vs. NP

P = NP? [Cook 1971, Edmonds, Levin, Yablonski, Gödel]

O problema de decisão é tão fácil quanto o problema de verificação?

Se sim… Algoritmos eficientes para Caixeiro Viajante, Cobertura de vértices, …

Se não… Sem algoritmos eficientes para Caixeiro Viajante, Cobertura de vértices, …

Consenso. Provavelmente não.

Como saber em que classe cada problema está?

  • Fazendo uma análise do problema e da (im)possibilidade de resolvê-lo eficientemente.


  • Comparando problemas através de redução!!!

Redução

Qualquer instância do problema A pode ser transformada (reduzida) em uma instância do problema B.
A solução do problema B soluciona também o problema A.

Problema A:
Dado um número,
adicionar 1 a esse número

Problema B:
Dados dois números,
somar os números

Redução Polinomial

Se o algoritmo que faz a transformação (redução) for eficiente (polinomial),
dizemos que esta é uma redução polinomial.

Problema A:
Dado um número,
adicionar 1 a esse número

Problema B:
Dados dois números,
somar os números

Relações entre Classes P e NP

Se o algoritmo que faz a transformação (redução) for eficiente (polinomial),
dizemos que esta é uma redução polinomial.

Todo problema da classe P também está em NP.

Existem problemas na classe NP que são “os mais difíceis de resolver eficientemente”, no sentido que qualquer outro problema de NP pode ser reduzido a eles.

Estes problemas formam a classe de problemas NP-completos.


P = NP?

Exemplos de Problemas NP-Completos

➞ Planejar um roteiro de viagem visitando algumas cidades de interesse de forma a minimizar o trajeto percorrido

➞ Determinar quantas cores são necessárias para colorir um mapa tal que países que fazem fronteira não tenham a mesma cor.

Exemplos de Problemas NP-Completos

➞ Montar uma mala com no máximo 23kg, tendo um conjunto de itens para carregar, sendo que cada item possui um valor agregado e queremos que a mala tenha o maior valor possível

➞ Alocar convidados a mesas tal que amigos sentem juntos e inimigos separados

Exemplos de Problemas NP-Completos

➞ Solucionar problemas Sudoku, Tetris, Minesweeper, Batalha naval, …


Considerações sobre Complexidade

  • Se sabemos que um problema não tem solução eficiente (em P ou no máximo em NP), nem adianta procurar essa solução…


  • Se sabemos que um problema está em NP-completo, temos que avaliar se é possível usar um algoritmo exato (somente se forem usadas apenas instâncias bem pequenas do problema) ou se temos que usar algum algoritmo que dê uma resposta aproximada.


  • Grande parte dos algoritmos de criptografia usados hoje são baseados em problemas NP-completos, se P = NP poderíamos ter grandes problemas de segurança…
